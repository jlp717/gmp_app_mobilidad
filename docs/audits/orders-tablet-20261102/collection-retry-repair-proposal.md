La prueba existente `commercial retry keeps its token but an account change scopes a new attempt` pasa 1/1 con exit 0 y demuestra que `setAuthToken` cambia la clave después de un timeout. El mismo método se ejecuta al renovar el token de la misma cuenta. Un cobro parcial persistido cuya respuesta se perdió podría registrarse otra vez con la nueva clave. El login público de otra cuenta desmonta el panel. El problema reproducible se centra en la renovación ordinaria y en la retención indefinida de intentos ambiguos.

La propuesta conserva cada intento en la caja cifrada de Hive que la aplicación ya sabe abrir. Usa una clave opaca por documento, huellas HMAC sobre el contenido canónico y un token estable por intento. Conserva el cuerpo exacto cifrado, sin credenciales de sesión. El identificador de la cuenta es estable y la versión del token sólo protege el transporte. Antes del POST se persiste el intento. Si se pierde la respuesta o se cierra la app durante el envío, se recupera el mismo cuerpo y token. Un reintento con otro importe, método o notas para ese documento queda bloqueado hasta comprobar el anterior. Otra cuenta recibe un aviso sin detalles del intento original.

La caja admite como máximo 64 registros. Al alcanzar el límite, el comercial puede comprobar un intento existente. Los resultados ambiguos conservan su token sin caducidad. Sólo una respuesta inequívoca del servidor al envío original o a su repetición exacta puede resolverlos. Un saldo inferior por sí solo no atribuye el cobro a ese intento. Tras un ACK exacto, una lectura nueva del saldo habilita otro cobro parcial explícito. Un fallo de almacenamiento bloquea el POST. Sólo una prueba de cero despacho permite liberar un intento nuevo reservado.

El estado de sesión publicado por Flutter incluirá el epoch del transporte, después de instalar el token. El panel reconstruirá las páginas financieras al cambiar ese contexto, incluso si vendedor, rol y versión de permisos son los mismos.
